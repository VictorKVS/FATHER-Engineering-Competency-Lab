# FATHER Product Incubation Portfolio

**Portfolio ID:** FATHER-PORTFOLIO-0001  
**Status:** ACTIVE PORTFOLIO / FUTURE PRODUCT INCUBATION  
**Purpose:** preserve detailed product seeds now and launch them one by one as FATHER, its agents, knowledge systems and evidence gates mature.

> A product seed is not shipped functionality. `IDEA / PRESERVED / RESEARCH / QUEUED` must never be presented as an MVP.

## Lifecycle

`IDEA → PRESERVED → RESEARCH → QUEUED → EXPERIMENT → PROTOTYPE → MVP → PRODUCT → SCALE`

Promotion requires evidence. Every future product receives a passport containing problem, users, value, inputs, outputs, dependencies, architecture hypothesis, security/privacy, knowledge requirements, agent roles, MVP boundary, evidence gates, business hypothesis, presentation plan and protection class.

## Launch policy

A seed is launched only when prerequisite FATHER capabilities are mature enough. Priority is determined by: strategic value, reuse of existing components, training value for agents, availability of evidence/data, implementation cost, security/legal risk, time to demonstrable MVP and portfolio synergy.

Each completed MVP should produce three outputs:

1. **PRODUCT** — working bounded capability.
2. **LEARNING** — measured experience for Programmer/Architect/Security/QA/etc.
3. **FACTORY ASSET** — reusable patterns, tests, components and knowledge.

Public GitHub/showcase receives only evidence-backed capabilities and presentation-safe material. Proven high-value nodes, weights, routing, golden patterns, decision intelligence and competitive learning mechanisms may be classified INTERNAL / CONFIDENTIAL / FATHER-CORE rather than published.

## Standard seed passport

Every new idea added to this portfolio should eventually receive its own file with:

- ID / title / owner / status / protection class;
- problem and target users;
- value proposition and non-goals;
- evidence that the problem exists;
- inputs / outputs / data provenance;
- functional and non-functional requirements;
- architecture hypothesis and alternatives;
- dependencies on FATHER components and knowledge bases;
- required agent roles and minimum competency levels;
- security, privacy, legal and abuse analysis;
- MVP boundary and explicit exclusions;
- test/evidence/promotion gates;
- metrics: quality, time, cost, defects, autonomy, transfer;
- business/monetization hypothesis where relevant;
- presentation assets required for the showcase;
- lessons/factory assets expected after completion.

## Showcase policy

When a seed reaches evidence-backed MVP, prepare a premium public presentation package:

`Hero visual → Problem → Why now → Demonstrable capability → Architecture → Evidence → Demo/Quick Start → Limitations → Roadmap → Ecosystem links → Security/Trust → Metrics`

The presentation may be visually ambitious, multilingual and product-oriented, but must never turn a roadmap item into a shipped capability.

Do **not** start all portfolio items. Current priority is to make FATHER-TRAIN-0001 demonstrate measurable learning and transfer. As factory components mature, promote the next seed deliberately, one at a time, using readiness and portfolio value rather than excitement alone.
