# FATHER Chassis — правила оформления коммитов

Коммиты должны быть понятны человеку, который откроет историю проекта через несколько месяцев и не помнит текущий контекст.

## Общий принцип

Коммит должен отвечать на четыре вопроса:

1. **Что изменено?**
2. **Почему это было нужно?**
3. **Как именно это реализовано?**
4. **Чем подтверждена работоспособность?**

Короткие сообщения вида `fix: bug`, `feat: api`, `update tests` не считаются достаточными для значимых изменений.

## Рекомендуемый формат

Первая строка — краткое человеческое резюме изменения.

Далее через пустую строку — подробное описание.

Пример:

```text
FATHER Factory: добавлен квалификационный протокол для каждого запуска агента

Что изменено:
- добавлен FactoryQualificationRecord;
- в протокол записываются requirement_id, agent_id, build plan и provider bindings;
- сохраняются trace_id, workflow_id, evidence hashes и policy decisions;
- результат квалификации снабжается собственным SHA-256 record_hash;
- FactoryExecutor теперь автоматически возвращает qualification вместе с результатом исполнения.

Зачем:
До этого фабрика могла собрать и запустить агента, но не формировала единый доказательный артефакт,
который связывает требования заказчика, конкретную сборку, исполнение, evidence и audit.

Проверка:
- добавлен test_factory_qualification_record.py;
- тест включён в общий prototype_vertical_test.ps1;
- modular API qualification проверяет qualified=true и наличие record_hash.

Результат:
Factory Execution теперь имеет воспроизводимое доказательство квалификации конкретной сборки агента.
```

## Для архитектурных изменений

В сообщении отдельно указывать:

- какой архитектурный контракт или слой затронут;
- какие компоненты остаются совместимыми;
- есть ли migration / rollback;
- какие ограничения остаются;
- какой qualification gate должен пройти после изменения.

## Для исправлений

Обязательно указывать:

- наблюдаемый симптом;
- корневую причину;
- исправление;
- регрессионный тест.

## Для инфраструктуры

Указывать:

- что меняется в Docker / Compose / storage / network / security;
- влияет ли изменение на non-root runtime;
- требуется ли пересоздание контейнера или volume;
- способ отката.

## Для квалификационных коммитов

Указывать реальные подтверждённые результаты, например:

```text
Qualification:
- 29/29 Python tests PASS
- modular API 9/9 PASS
- real local model inference PASS
- Factory Execution PASS
- Qualification Record PASS
```

Не писать `PASS`, если результат ещё не был фактически получен.

## Принцип FATHER

> Ни один компонент не считается готовым, пока не доказана его работоспособность в составе конечного изделия.

История Git должна отражать не только изменение кода, но и путь доказательства его работоспособности.
